# 归并评估集

> 对应 `docs/status.md` §3 路线图 5「评估集」与 §5 开放问题「评估集标注工具」。
> 工具：`scripts/eval_merge.py`（CSV + 脚本，无 web 界面，无 LLM）。

## 为什么需要它

归并层（`newsassistant/merge.py`）是系统的心脏：召回 + LLM 裁决把新文档归档进
Story。它是全系统里最容易"看起来合理但实际错了"的一层——错并把两个不同事件
糊成一个，漏并让本该合流的报道各自为政，dashboard 上的 velocity/breadth/consensus
全部失真。没有评估集，任何 prompt 改动、模型换选、召回策略调整都是凭感觉调
（v1 的死因之一）。目标：先攒几天真实数据，人工标 ≥200 篇文档的正确归属，
之后所有归并层改动都对着这个集合跑分再合入。

## 工作流

```bash
# 1. 导出待标注 CSV（默认最近 200 篇已抽取文档）
.venv/bin/python scripts/eval_merge.py export --out eval.csv

# 2. 人工在 Excel / Numbers / 任意编辑器里打开 eval.csv，逐行填两列：
#    label_story_id（必填，见下）、label_note（可选，写判断依据方便复核）

# 3. 打分
.venv/bin/python scripts/eval_merge.py score eval.csv
```

`export` 只读，不写库；每次都是当前状态的快照。可以反复导出——不会污染数据。

## CSV 列与标注取值

每行一篇已抽取文档（`documents.extracted_at IS NOT NULL`）。列：

| 列 | 含义 |
|---|---|
| `doc_id` / `published_date` / `source_key` / `title` | 文档基本信息 |
| `claim_1..3` | 前 3 条抽取出的断言，帮助判断这篇在讲什么 |
| `current_story_id` / `current_story_title` | 系统**当前**把它归进了哪个故事（可能为空——还没跑过 `na assign`，或本来就该独立成新故事） |
| `cand1..3_id` / `cand1..3_title` | 召回阶段给出的 top-3 候选故事（复用 `merge.recall()`，与系统裁决时看到的候选一致） |
| `label_story_id` | **人工填**。见下 |
| `label_note` | **人工填**（可选）。写清楚判断依据，复核时不用重新查一遍原文 |

`label_story_id` 三种取值：

- **已有 story 的数字 id**：这篇文档应该归入这个故事（不管系统实际归到哪，
  也不管这个 id 是否出现在候选列表里——候选列表只是给标注者参考，人工判断
  不受候选范围限制）
- **`new`**：这篇应该独立成一个新故事，不与本次标注集里的任何其它文档同故事
- **`same:<doc_id>`**：这篇应该与另一篇文档 `<doc_id>` 同故事，但两篇眼下都还
  没被系统归并（`current_story_id` 都是空），所以标不出一个具体的 story id，
  只能标"这两篇应该在一起"。`doc_id` 必须是本次导出集合里出现过的文档 id

留空 = 未标注，`score` 会跳过（不计入准确率分母）。

## 标注规范 —— 必须与裁决器判据一致

`score` 测的是"系统的归并结果多接近人工判断"。如果标注者用的判断标准和
`newsassistant/merge.py` 里 `JUDGE_PROMPT` 用的标准不是同一套，分数就是在比较
两个不同的问题，评估失真。标注时套用 `JUDGE_PROMPT` 的原话：

- 同一个**持续事件或进程**的报道属于同一故事（同一次地震的后续伤亡更新、
  同一项法案的各阶段、同一场谈判的多轮）
- **仅主题相似不构成同一故事**：两次不同的地震是两个故事；两家公司各自的
  裁员是两个故事——这是最容易标错的地方，也是最能检验裁决器的地方
- 后续报道、更正、回应、分析评论都跟随其针对的事件，不独立成新故事
- 人工标注**不适用**"拿不准选 new"这条（那是给 LLM 裁决器兜底用的，标注者
  的职责就是给出正确答案）；实在拿不准，在 `label_note` 里写明理由，之后
  抽查/仲裁，不要靠猜

## 目标样本量与取样注意事项

- 目标 ≥200 篇，`export --limit` 默认就是 200
- **跨源同一事件的例子必须够多，否则评估没有区分度**：如果标注集里全是
  "每篇文档各自一个新故事"的样本，任何召回策略（甚至全部召回失败、逐篇新建）
  都能拿到高分——因为压根没有真正需要合并判断的案例。用 `export --source`
  分批导出多个源，或直接从已经有多篇报道的活跃事件里挑，保证集合里既有
  "应该合并"又有"表面像但其实是两个事件"（hard negative）的样本
- 覆盖已归并（`current_story_id` 非空，用来检验系统实际做的对不对）和未归并
  文档（用 `same:` 标注，检验"如果现在跑 assign 会不会分错"这种前瞻性场景）
- `--since` 可以只导出某个时间窗，方便分几天陆续标注、逐步凑够 200 篇

## `score` 输出与口径

```bash
.venv/bin/python scripts/eval_merge.py score eval.csv [--json]
```

- **准确率**：已标注文档中，与其它任意已标注文档的两两关系（该合/该分）都
  与系统实际结果一致的文档占比。不是简单的"story_id 是否相等"，因为 `new`
  和 `same:` 语义下未必有一个具体 id 可比——统一转成"两篇文档是否应该同故事"
  的判断后按文档打分更准确也更好懂
- **错并数**（系统合了人说该分的）：一对文档，人工认为应该是两个不同故事，
  系统却把它们放进了同一个 story
- **漏并数**（系统分了人说该合的）：一对文档，人工认为应该同故事，系统却
  分到了不同 story（含其中一篇/两篇都还没被系统归并的情况）
- **按来源/日期分桶**：同样的文档级准确率，按 `source_key` / `published_date`
  分组统计，用来定位"某个源的文章特别容易被错并"或"某天的新闻密集导致召回
  窗口不够用"这类系统性问题
- 未标注行（`label_story_id` 为空）不计入统计；非法标注（既不是数字、不是
  `new`、也不是合法的 `same:<id>`）会单独列出 `invalid_labels`，不会被静默丢弃

打分逻辑是纯函数 `eval_merge.score_rows()`（输入行列表，输出统计 dict），
不碰数据库，测试见 `tests/test_eval_merge.py`。

## 注意事项

- `score` 会重新查一次 `story_documents`，用的是**当前**系统状态，不是
  `export` 时快照里的 `current_story_id` 列（那一列只是给标注者参考用）。
  如果标注期间又跑过 `na assign`，打分反映的是最新状态，属预期行为
- `same:` 语义依赖两篇文档都在同一次 `export` 里；如果分批多次导出，
  `same:` 引用的另一篇 doc_id 未必在被打分的这份 CSV 里——脚本仍会正确处理
  （只要那个 doc_id 本身有对应的行参与打分；如果它根本没被标注，这对关系
  就不会被纳入统计，不会报错）
- 这套工具全程不调用 LLM；裁决模型选型（haiku 是否够用）的 A/B 实验，是拿
  同一份标注集在不同模型下各跑一轮 `na assign` 后对比 `score` 结果，工具本身
  与模型无关
