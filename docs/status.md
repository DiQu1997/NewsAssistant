## 1. 决策日志（为什么是现在这个样子）

按时间序记录关键决策与理由。推翻任何一条前先读它的理由。

| # | 决策 | 理由 |
|---|---|---|
| D1 | **放弃 v1 的无状态聚类，改为"召回 + LLM 裁决"的归档** | v1 死因：新闻语义空间无簇结构（KMeans 实验失败，见 legacy/ 提交历史）；事件是有身份、会分裂合并的持续对象，无状态批量聚类建模不了 |
| D2 | **硬编码结构，永不硬编码主题** | 带主题先验的系统只能看见构建者想到的东西。结构先验（文档有断言/断言有信源/实体有身份）通用且廉价，主题（领域词汇、实体清单）必须由数据涌现 |
| D3 | **频道 = 保存的查询；一个通用存储** | 一个故事天然属于多个领域（出口管制 = 半导体+地缘+宏观）；分区存储会强迫单一归属。新频道 = 加一行查询，零新代码（已由"全库分歧"元频道验证） |
| D4 | **视图由数据结构自动选择，不由人声明** | 网络/链路/阶梯/共轴时间带各配一种数据形态（无向稠密关系/可拓扑排序的有向边/有序状态机/可对齐外生序列）。人工声明"半导体=链条"又是主题先验 |
| D5 | **编码语法全局不变**：色阶=密度、▲▼=方向、蓝↔红+字符=立场、状态色只表越阈、形状=实体类型 | 编码含义换频道就变意思，产品即废。共用的是语法不是版面 |
| D6 | **禁止 LLM 解析 HTML**；正文抽取用 trafilatura | v1 用 scrapegraphai 逐页跑 GPT，成本与脆弱性差数量级。LLM 只花在理解上 |
| D7 | **正文存文件（内容寻址），库里存指针** | 大文本不进主表；sha256 寻址天然做精确去重 |
| D8 | **三级去重：URL 规范化（保守）→ sha256 → simhash 近重** | 规范化过度会把不同文章折叠成一条，比漏合并更糟，所以只做确定安全的变换。simhash 只标**候选**（near_dup_of），转述判决属于阶段 3 裁决 |
| D9 | **抽取走 Claude Agent SDK（CLI 登录态）而非 API key** | 计费到订阅（用户明确要求）。已在云端会话真实验证 |
| D10 | **强 schema 走工具调用**：模型只有一个 submit_extraction 工具，无文件/网络工具 | schema 校验发生在工具层，比"请输出 JSON"可靠 |
| D11 | **每次 LLM 调用落 llm_calls，含失败与完整 usage** | 可审计是底线。教训：SDK 报的 input_tokens=38 极具误导（cache_read 实为 61825），只存两个数字会完全误判成本 |
| D12 | **故事页每句综述必带引用标记**；独立信源数必须做转述溯源 | "187 篇报道"的真相可能是"3 个独立源 + 184 次转发"；广度指标的命门 |
| D13 | **地缘频道不画手绘世界地图** | 手绘海岸线无法保证准确；插满新闻圆点的地图信息量≈0。位置由走廊命名承载；生产版接真实地理图层 |
| D14 | **绝不双纵轴**；量纲不同的序列归一化到基期 100 共轴，终点直标 | 双轴凭空制造相关性。背离度只比幅度不比方向（无符号强度 vs 有符号收益率不可直接相减） |
| D15 | **热力图分位分档**（非线性/对数），阈值明示图例 | 日报道量动态范围仅 ~10 倍：线性压低段、对数推高段；分位让六档都被用上 |
| D16 | **配色必须过 dataviz 校验器** | 四个频道标识色无法同过全对 CVD 检查（紫↔蓝 ΔE 9.8）→ 实体类型改形状编码，颜色让给频道标识。凭眼睛挑色不可靠 |
| D17 | **数据的长期归宿是用户本机**；云端会话是临时开发容器 | 云端容器闲置即回收、出站受环境网络策略限制。repo（代码+文档+CLAUDE.md）是会话间的接力棒 |
| D20 | **SDK 会话必须裁剪：批量打包 N 篇/调用 + 禁用全部内置工具** | 每次 query() 是完整 Claude Code 会话，底盘（系统提示+34 个工具定义）~68k tokens，是 700 token 文章的 60 倍。批量+全禁后每篇 ~2-3k，降 15-20 倍。审计表（D11）给出的实测 |
| D21 | **召回按 IDF 降权；裁决以候选标题核心事件为锚；digest 文档不并入** | 真实事故：泛化实体（United States 出现在 10% 文档）等权召回 + 多主题简报文档 → catch-all 故事滚雪球，局部每步合理全局错。错并靠人工拆（split 事件留痕），预防靠这三条 |
| D18 | **API 类源 = 一个适配器（响应→条目）+ 共用管线**；查询参数是数据不是代码 | 没有 feed 的源不该长出第二条采集管线。适配器只负责"这个 API 的响应长什么样"（协议细节），去重/落盘/日志全部复用 —— 换源只加一个适配器，代码里没有一处按主题分支 |
| D19 | **HTTP 通道（httpx/curl/auto）是源的属性，不是代码里按 host 的分支** | SEC 在 TLS 指纹层拒绝 httpx 而放行同 UA 的 curl。是否被拦取决于部署环境（云端 MITM 代理会掩盖差异，本机会撞上），所以给源一个 `fetch_via`，`auto` 让它自己在被拦时换通道 |

### ✅ 阶段 1 · 采集层（newsassistant/，001_core.sql）

### ✅ 阶段 1.5 · API 类源（004_api_sources.sql, apisources.py）

下游管线完全复用；源新增两个结构属性 `adapter` 与 `fetch_via`（httpx/curl/auto）。
首个适配器 `edgar_fulltext` 走 EDGAR 全文检索 JSON（`q` 留空 = 无主题过滤，
按备案时间倒序，每页 100 条），min_interval=1s + UA 带联系邮箱满足 SEC 合规。
真实验证：一轮拉到 50 篇 8-K（NA_MAX_ITEMS 上限），0 错 0 重，二轮 0 新增。

### 测试：25/25 通过，全部无外网依赖

## 3. 路线图

### ⬜ 阶段 3 · 归并层（下一步 —— 系统的心脏）

1. **召回**（纯确定性，零 LLM 成本）：对新文档取候选故事 top-K
   - `document_entities` 倒排命中（已就位）
   - 时间窗过滤（活跃故事池）
   - 文本相似（先词面 / trigram，pgvector 向量召回后置）
2. **裁决**（Agent SDK 单步，同抽取的强 schema 模式）：
   "属于故事 X / 新故事 / X 的分支？" → 判据（引用的 claim/实体重叠）落 `story_events`
   —— 系统必须能回答"为什么这篇归到这个故事"
3. **Story 状态增量维护**：velocity（报道量变化率）/ breadth（独立源数，
   用 near_dup_of + syndication_of 溯源后计数）/ consensus（claim 立场方差）/ stage
4. **故事生命周期**：active →（N 天无新文档）dormant → archived；分裂/合并走 story_events
5. **评估集**：攒几天真数据后人工标 ≥200 篇的正确归属；之后所有归并改动对着测

### ⬜ 阶段 4 · 合成层
活跃故事的 running summary（每句带 claim 级引用）、开放问题生成、事件切分
（时间锚定的状态变化，故事页时间线的数据源）、转述判决（simhash 候选 → syndication_of）。

### ⬜ 阶段 5 · 前端真化
dashboard 从 store.mjs 假数据切到 Postgres 物化视图/快照表；频道切换真化；
实体页；结构检测从真实抽取产物识别（哪些实体间存在稳定有向依赖等）。

### ⬜ 之后（顺序未定）
pgvector 向量召回（新迁移）· 实体消歧裁决（召回+LLM，同归并模式）·
sitemap/bulk 类源接入（API 类已就位，见阶段 1.5）· L3 数值源入库
（sensors 表）与叙事对齐 · 频道涌现提议 · 日报/推送 · Batch 化抽取降本

## 5. 开放问题（需要拍板或研究）

- **产品范围**：四频道全做已定，但**每日实际使用的入口**是哪个？（brief 推送 /
  打开 dashboard / 按需报告）—— 决定合成层的优先级
- **评估集标注工具**：人工标 200 篇归属用什么界面？（最简：CSV + 脚本）
- **裁决模型选择**：归并判断用 haiku 够不够？需要真数据 A/B（llm_calls 已备好审计基础）
- **故事分裂/合并的触发**：裁决时顺带判断，还是独立的定期审视 pass？
- **转述溯源算法**：simhash 候选 + 时间先后 + 措辞继承的具体判决规则；
  跨语言转述（外电中译）怎么判
- **L3 数值源的 schema**：现在 documents 一张表装所有；数值观测（地震/价格）
  是否需要独立的 observations 表与故事对齐机制
- **频道涌现的阈值**："持续、密集、跨源、不属于任何现有频道"的量化定义
- **多用户**：当前单用户设计；朋友共用是否需要（影响频道配置的归属）
- **成本预算**：真实量级（日几百篇）下抽取+归并的订阅额度消耗，跑几天真数据后测

## 6. 已知风险与限制

- ~~云端会话出站受限~~：网络策略已改 Full（2026-07-27），种子源实测可达
- **反爬拦截页会污染语料**（真实教训）：Federal Register 文档页对 bot 返回统一
  "Request Access" 页，50 篇入库成 49 篇 dup_exact 垃圾。修复：源注册表新增
  fetch_article 属性（feed 即载荷的源不抓页面），受污染数据已清除重采
- **pgvector 未装**（云端容器无该扩展）：001/002 迁移刻意不依赖它；向量召回的
  003 迁移需要 pgvector/pgvector:pg16 镜像或本机安装扩展
- **simhash 对短文本敏感**：几十词快讯改三词即超阈值 —— 判定为特性（快讯改三词
  不该算同一篇），但转述溯源在短文上会漏召回
- **部分 L1/L3 源正文抽取退化为 feed 摘要**（USGS/arXiv/SEC 页面结构特殊）——
  已有回退逻辑，meta.extracted=false 标记；对这类源摘要即全部载荷，属预期行为
- **feedparser 对畸形 feed 的容错未经真实源大规模检验**（网络放开后首要观察点）
- **原型的"结构检测"检测的是已典型化的结构**：生产版需从抽取产物中识别
  （实体间稳定有向依赖如何从 claims 中涌现 —— 阶段 5 的真正难题）
